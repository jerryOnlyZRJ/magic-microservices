# 设计理念

Magic 不只是一个把模块注册成 Custom Element 的工具函数，它背后是一套很明确的设计判断：**尽量把微前端能力压回浏览器原生抽象，把框架差异收敛成统一接口，把上层玩法留给业务和生态去定义。**

## 为什么要做 Magic

很多微前端方案更偏向“应用编排”，擅长处理主子应用、路由切换和整页组合。但在大量真实业务里，团队更需要的是一种更轻、更小、更容易渐进接入的模块化能力：

- 不改造整套平台，也能把一块能力独立交付
- 不统一技术栈，也能把不同框架实现复用到同一个宿主里
- 不引入复杂协议，也能像使用 HTML 标签一样消费模块

Magic 的目标正是把这件事降维成一个更直接的开发模型：**改造模块、注册模块、使用模块。**

## Web Components Plus

Magic 的第一层理念不是替代 Web Components，而是站在它之上做增强。

- 保留浏览器原生 Custom Elements 的标准化消费方式
- 保留 HTML 标签作为统一交付协议
- 保留浏览器作为最终运行时边界
- 在此基础上增强数据透传能力，让 `Object`、`Function` 等引用类型也能安全传递

这也是为什么 `useProps()` 很重要。Magic 不希望为了透传复杂数据而把用户对象序列化成另一种形态，因为那会破坏引用、原型链和真实语义。Magic 的选择是让增强能力仍然服务于原始模型，而不是篡改它。

## 薄桥接层，而不是重平台

Magic 的第二层理念，是把自己定位成一个**足够薄的桥接层**。

与很多“接管式”方案不同，Magic 不试图变成新的大一统平台，也不要求你先学习一整套复杂基础设施。它更像一个贴近浏览器的底层基建能力：

- 一个 `magic()` 函数完成注册
- 一套生命周期承接已有模块逻辑
- 一个 HTML 标签成为最终消费协议

这意味着 Magic 的学习路径是渐进式的。你先学会最小闭环，就能把能力用起来；只有在需要更复杂定制时，才继续理解插件、事件流、沙箱等上层扩展。

## JS Module 即实体，粒度不设限

Magic 不预设“微前端”必须是一整个应用。它更强调：**只要是一个可交付、可挂载、可复用的前端模块，它就可以成为微前端单元。**

因此它天然支持更细粒度的拆分方式：

- 一个用户卡片组件可以是微前端
- 一个富交互面板可以是微前端
- 一个远端加载的业务模块也可以是微前端

这种设计把“微前端”从应用级概念拉回到了“能力单元”视角，也让团队可以按组件、按模块、按业务边界逐步推进，而不是一次性重写架构。

## 抹平框架，而不是制造新框架

Magic 的核心价值不是替代 React、Vue、Svelte 这些框架，而是**抹平它们的接入成本**。

你可以把它理解成一层统一接口：

- 组件开发方使用自己最合适的技术栈
- 组件消费方只面对统一的标签协议和生命周期约定
- 宿主系统不再需要为每一种框架单独维护一套胶水层

这种设计让“一处编码，随处复用”成为现实，也让团队能在特定场景里选更合适的技术实现，而不是被项目初始框架永久绑定。

## Core 保持克制，Plugin 负责扩展

Magic 还有一个非常重要的边界意识：**Core 只做 Web Components 封装和运行时最小能力，扩展性交给 Plugin。**

这样设计有两个好处：

- Core 更稳定，职责更单一，不轻易把业务定制写死在底层
- Plugin 更自由，团队可以围绕适配、数据加工、运行时增强、沙箱等需求做自己的扩展

从这个角度看，Magic Plugin 更像“适配器层”。它负责把不同宿主诉求、不同集成环境、不同工程约束接到同一套核心能力上，而不是把所有逻辑都耦合进运行时内核。

## Meta Framework 的方向

Magic 想解决的长期问题，不只是“如何注册一个组件”，而是：**如何让框架不再成为前端协作的第一约束。**

在这种视角下，Magic 更接近一个 Meta Framework：

- 它不拥有一整套独占生态
- 它更像不同框架生态之间的连接层
- 它鼓励团队在不同场景里选择更合适的实现
- 它试图降低跨框架复用和组合的成本

这并不意味着团队可以无节制混用技术栈。相反，Magic 提供的是“有能力这样做”的自由，而不是“默认应该这么做”的鼓励。真正的工程价值，在于让架构选择回到业务目标、性能目标和团队协作本身。
