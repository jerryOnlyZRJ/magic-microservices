# 核心能力

在 Magic 的文档结构里，核心能力层回答的是一个更务实的问题：**当你接受了它的设计理念之后，真正拿来落地的最小能力集合到底是什么。**

Magic 的核心能力并不追求“大而全”，而是强调一个足够小、却又足够完整的运行时闭环。

## 最小闭环：注册、挂载、消费

Magic 的第一组核心能力，是把模块交付压缩成浏览器能直接理解的过程：

- 用 `magic()` 把模块注册成 Custom Element
- 用生命周期承接已有业务逻辑
- 用 HTML 标签作为最终消费协议

这也是为什么 Magic 的落地门槛会明显低于应用级编排方案：你不需要先学主子应用治理，先把一个可复用模块跑起来就足够开始。

## 生命周期是运行时边界

Magic 不把能力埋在隐式框架机制里，而是显式地通过生命周期暴露边界：

- `bootstrap` 负责启动前准备
- `mount` 负责首次挂载
- `updated` 负责属性变化后的更新
- `unmount` 负责副作用清理

这样的边界让模块的职责更容易推理，也为插件、适配器和后续运行时增强留出了稳定的挂载点。

## Props 是浏览器模型上的增强

Magic 的另一组核心能力，是在不背离 Web Components 的前提下增强数据流：

- 通过 `propTypes` 明确声明模块可消费的数据契约
- 通过 `useProps()` 传递对象、函数等引用类型
- 保持标签消费方式不变，同时避免把复杂数据退化成字符串

这正是 Magic 区别于纯 Web Components 封装的关键点之一。它不是重新发明一套组件协议，而是在浏览器协议上补齐真实业务落地需要的能力。
